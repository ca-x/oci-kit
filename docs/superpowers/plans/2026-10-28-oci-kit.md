# Initial implementation plan

Implement locally in this session. The applicable requesting-code-review skill
requires a bounded read-only reviewer; implementation is not delegated. The user
has authorized committing and pushing each completed phase to the primary branch.

1. Implement the generic source document and verified atomic downloader in
   `crates/oci-kit/src/fetch.rs`; exercise it with local HTTP fixtures.
2. Implement read-only tar inspection in `crates/oci-kit/src/inspect.rs`; test
   normalization and compression without extracting an untrusted archive.
3. Implement protected offline staging and explicit deletion plans in
   `crates/oci-kit/src/staging.rs` and `clean.rs`; test symlink and mount refusal.
4. Implement the explicitly LightOS-specific adapter in `crates/lighos-init`.
   Install into staging, preserve platform account/SSH ownership, restore only
   declared keyrings after platform setup, and write completion state last.
5. Implement Pond-only latest-source resolution and policy in `pond-oci`, then
   use the generic downloader. Inspect the real payload before choosing removals.
6. Run formatting, clippy, tests and docs; document independently what is built,
   what has been executed, and what still needs a LightOS launch test.

## Review focus

- A corrupt or interrupted download cannot replace a verified destination.
- `../`, symlinked ancestors, `/` and mounted paths cannot be cleaned.
- A staging marker is explicit; a dry run performs no deletion.
- No seed/password is baked into layers or placed in command-line arguments.
- Neither Pond release parsing nor its package list enters generic binaries.

## Execution rules

Continue under the user-requested `ub-mode`: reproduce failures before fixing
them, keep mechanisms separate from recipes, verify one phase before starting
the next, and record actions and evidence in `WORK_LOG.md`. Commit and push each
verified phase. Do not publish third-party rootfs or OCI artifacts without a
separate redistribution decision.
